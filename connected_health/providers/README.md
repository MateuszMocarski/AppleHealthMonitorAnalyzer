# Health Data Providers

`connected_health.providers` owns provider-specific ingestion for Connected Health
Analyzer. A provider understands one external export format, validates and normalizes it,
then returns the shared canonical `HealthData` model. Shared analysis and report
generation begin only after that boundary. The project requires Python 3.14 or later.

```text
provider export
    ↓
provider-owned import / parse / normalize
    ↓
HealthDataProvider.load(...)
    ↓
LoadedHealthData
    ├── HealthData
    ├── DatasetProvenance
    └── ProviderLoadDiagnostics
    ↓
ReportGenerationApplication → HealthAnalyzer → report renderers
```

The hard boundary is: provider-specific identifiers, source-selection rules, export
metadata, and parser intermediates must not enter shared analyzers or renderers.
`DatasetProvenance` and diagnostics are adjacent to the canonical data for orchestration
and presentation; they do not alter report calculations or JSON schema `1.0`.

## Current provider

Apple Health is the only implemented health-data provider.

`AppleHealthProvider` accepts an Apple Health export ZIP, opens the eligible XML stream,
and returns `LoadedHealthData`. Its responsibilities include:

- ZIP and export-XML validation and streaming;
- Apple `HK*` identifier mappings and sleep-stage normalization;
- Apple Watch and Apple Health source-name selection;
- Apple-specific input errors and load diagnostics; and
- normalization into canonical `HealthData`.

Apple source policy belongs to `AppleProviderConfig` / `AppleSourceConfig`. The shared
`AnalysisConfig` contains provider-neutral analysis settings such as sleep scoring.
Apple source selection stops before `HealthData`, so `HealthAnalyzer`, report models,
`TextRenderer`, `JsonRenderer`, and Viewer rendering do not branch on Apple-specific
data.

The following compatibility surfaces remain intentionally stable:

- `provider_id = "apple_health"`;
- `apple_watch_source` and `apple_health_app_source`;
- TOML `[source]`;
- the Apple text-report title;
- JSON schema `1.0`; and
- existing managed Drive `ahm_*` metadata.

The browser presents an explicit provider choice, but its generation request currently
uses the Apple Health workflow. There is no general backend provider-dispatch contract
and no provider-aware persisted-report identity today. Google Drive is optional identity
and storage infrastructure, not a health-data provider.

## Provider contract

The provider contract is defined in [contract.py](contract.py):

```python
class HealthDataProvider(Protocol):
    provider_id: str

    def load(self, path: Path, *, config: object) -> LoadedHealthData: ...
```

`LoadedHealthData` contains canonical `HealthData`, immutable provenance, and optional
load timings. Expected input failures are normalized through
`HealthDataProviderError(category)` so callers can map known provider failures without
depending on parser implementation exceptions.

## Adding a provider

When another provider is actually introduced, keep its importer, parser, raw mappings,
provider configuration, and source semantics in its own package under
`connected_health/providers/`. Normalize raw values into existing canonical domain
types before returning `HealthData`.

Preserve these rules:

- missing values remain missing and measured zero remains zero;
- numeric values must be finite;
- provider identifiers and source/device rules do not leak into shared analysis;
- provider-only settings do not become `AnalysisConfig` fields; and
- shared reports are generated by the existing neutral application pipeline.

The provider should have focused input/error/normalization tests and run through the
shared report-generation pipeline without provider branches below `HealthData`. Public
browser dispatch or Drive identity changes should be introduced only alongside a real,
tested provider workflow—not as placeholders.
